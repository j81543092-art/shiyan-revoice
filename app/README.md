# 拾言 ReVoice

> 面向失语症患者的意图重建沟通助手 —— 把「AI 猜」变成「人确认」

华为 ICT 大赛第十一届创新赛 · 赛题一（基于华为云打造 AI 创新应用）· 05 方向

---

## 一句话

患者点几个图标、说一个词，AI 给出 3~5 个候选意图并排序，**最终由患者本人点选确认**。
AI 不替他说话 —— 这是整个产品的立意。

## 为什么需要它

失语症最容易被误解的地方是：**患者听得懂一切、想得明白，只是说不出来**。
国内失语症人群约 **310 万 ~ 570 万**（卒中患者 1494 万 × 患病率 21%~38%）。

现成的三类方案都卡在不同地方：

| 方案 | 卡在哪 |
|---|---|
| 通用语音助手 | 假设用户能把话说清楚，而患者恰恰说不清楚 |
| 传统 AAC 图板 | 静态符号查找，不根据线索推断意图，认知负担全在患者身上 |
| 大模型聊天机器人 | 直接给出断言式回答 —— 对患者就是「替他说话」，说错了他自己都没法纠正 |

**中间这道缝就是我们的位置**：从残缺的线索，推到完整的意图，这一跳目前没有产品在做。

```bash
cd app

# 打开
#   患者端   http://localhost:3000/
```


```bash
node scripts/seed.js --reset     # 或 npm run reset
```

```bash

```

跑机制契约回归（守住 R1~R8 红线，40 条）：

```bash

```

## 产品机制规格 R1~R8

这是产品的**对外契约**，改动须走 A 的规格变更。

| 编号 | 规则 | 内容 |
|---|---|---|
| **R1** | 候选数量 | 默认 3 个；线索充分（≥3 类线索）可到 4~5 个；凑不出 2 个有区分度的候选时触发澄清，**不硬凑** |
| **R2** | 排序与锁定 | 按综合置信度降序；**排序后位置锁定** —— 同一会话内同一批线索，候选位置不得变动 |
| **R3** | 置信度呈现 | 患者端不显示百分比数字，用排序位置表达；**家属端可见数值** |
| **R4** | 澄清触发 | ① top1 < 0.6 → 是/不是；② 前两名差值 < 0.1 → 二选一；③ 最多 2 轮，不收敛则展示全部候选 + 「都不是，重来」 |
| **R5** | 确认 | 患者点选候选即确认；进入「已表达」状态并朗读（可选），家属端实时同步 |
| **R6** | 紧急通道 | 疼痛/跌倒/呼救设首屏常驻一级大按钮，点击即通知家属端并留痕，**零模型调用** |
| **R7** | 个性化配置 | 家属/治疗师可增改词条；**紧急词不可删**；改动留痕可回滚；习得词须家属审核后生效 |
| **R8** | 输出措辞 | 第一人称口语短句（≤15 字）；禁用医学诊断措辞；禁止臆造线索中不存在的人名、药名 |

### 综合置信度公式（R2 的依据）

```
综合置信度 = 模型置信度 × 0.40 ＋ 场景先验 × 0.20 ＋ 线索覆盖度 × 0.25 ＋ 个性化加权 × 0.15
```

**不用模型裸分数排序** —— 裸分数不可校准，同样的线索换个问法分数就变。
场景先验与个性化加权是「懂这个患者」的证据：同一个「水」字，对一个患者是喝水、对另一个可能是吃药送服。

## 三条产品红线

### 红线一 · 紧急表达一键通道，不走 AI

疼痛、跌倒、呼救等紧急表达：首屏常驻大按钮，不藏在任何层级里；点下直达家属端通知流程，**零模型参与**。

线索中出现紧急词时规则置顶（词表匹配，不是模型判断）：

| 规则 | 触发条件 | 实现 |
|---|---|---|
| R6-① | 一级紧急词直接命中（跌倒了 / 喘不上气 / 救命…） | `emergency.js` |
| R6-② | 连点同一症状词 ×3 + 身体部位 | `emergency.js` |
| R6-③ | 二级紧急词 + 任一其他线索 | `emergency.js` |

> **命悬一线的事，不允许任何「AI 猜一下」。**

### 红线二 · 交互为人群身体条件让路

大图标、高对比、少层级、防误触。
WCAG 2.2 触控目标下限是 ≥24px，**我们按 84px 做**（患者手会抖）。
澄清按钮与候选按钮同级，不做成小字链接。

### 红线三 · 个性化有边界

紧急词不可删；习得词须家属审核后才生效；一切改动留痕可回滚。

适配层已就绪，**三种 provider 同一契约**，切换只改环境变量：

```bash
# 华为云 MaaS / ModelArts Studio（答辩正式环境）
# 认证是 Bearer API Key，不是 AK/SK 签名 —— 见下方说明
MODEL_PROVIDER=huawei \
HW_MAAS_API_KEY=... \
HW_MODEL_ENDPOINT=https://api.modelarts-maas.com/v2/chat/completions \
HW_MODEL=DeepSeek-V3

# 任意 OpenAI 兼容接口（联调过渡）

# 规则引擎（默认，零凭证，全链路照常可跑）
node server/index.js
```

未配置凭证时自动降级到规则引擎 —— **演示不中断**，评测数字照常产出。

### 华为云接入取数步骤（操作层面）

1. 登录华为云 **ModelArts Studio（MaaS）** 控制台，完成委托授权
2. **API Key 管理** → 创建 API Key（仅创建时显示一次，务必保存）
3. **预置服务** → 开通目标模型，状态显示「开通」即可用
4. 在该服务右侧 **「调用说明」** 复制 **endpoint** 与 **model 参数**
5. 写入 `.env`（模板见 `app/.env.example` ），启动即自动选用 huawei provider

### ⚠️ 一个容易搞错的点：AK/SK 与推理接口无关

华为云上有两套认证，早先的实现把它们混为一谈：

| 用途 | 认证方式 | 本项目是否需要 |
|---|---|---|
| **模型推理**（调大模型出结果） | `Authorization: Bearer {API_KEY}` | ✅ **需要的就是这个** |
| 管控面（开通服务、查配额、IAM） | AK/SK + SDK-HMAC-SHA256 签名 | ❌ 不需要 |

所以**光有 AK/SK 是调不通推理接口的**，必须去 MaaS 控制台创建 **API Key**。

> A 的战场在提示词与评测，不在模型内部。

## 验证方案与指标

自建评测集：每条样例带**场景 / 线索组合 / 标准答案 / 等价说法 / 应触发澄清**五要素。

判中口径：任一候选与标准答案或任一等价说法语义一致，记一次命中。
**没有「等价说法」就没法判命中** —— 语言有歧义，这是评测集最容易被漏掉的一列。

| 指标 | 口径 | 目标 |
|---|---|---|
| **Top-3 命中率**（主） | 标准答案出现在前三候选的比例 | 从约 30% 迭代至 60%+ |
| **平均澄清轮次**（辅） | 每次表达平均需要的澄清轮数 | ≤1 轮收敛 |
| P95 延迟 | 线索提交到候选展示的 95 分位延迟 | 满足现场可交互演示 |
| 缓存命中率 | 命中「线索组合 → 候选句」的比例 | 随使用上升 |

**当前基线（评测集 v1，20 条）—— 完整迭代曲线：**

| 指标 | 规则引擎 v1 | 规则引擎 v1.4 | 真实模型 v1.4 |
|---|---|---|---|
| **Top-3 命中率**（主） | 42.9% | **64.3%** | 42.9% / 57.1% / **71.4%** |
| 平均澄清轮次（辅） | 0.60 | 0.45 | 0.40 ~ 0.60 |
| 澄清判定正确率 | 50.0% | 50.0% | 25.0% |
| 紧急通道正确率 | 100% | 100% | 100% |
| 整体通过率 | 50.0% | 65.0% | 45.0% ~ 65.0% |

**真实模型那一列列出的是三次实测结果，不是区间估计 —— 因为目前它真的不可复现。**

同一份代码、同一个评测集，真实模型连续三次跑分：
**Top-3 = 71.4% / 57.1% / 42.9%**，整体通过率 65% / 55% / 45%。
差异**不是代码改了**（三次之间只有文档改动），而是模型输出本身在波动。

**这是本次最该被记住的一条结论：规则引擎的 64.3% 是可复现的，真实模型的数字目前不是。**
给一个单点数字会制造虚假的精确感。真实的现状是：
**必须先解决采样稳定性，真实模型的跑分才有讨论价值。**
在解决之前，**不应拿真实模型的数字去论证任何结论** —— 包括「它比规则引擎好」。

「真实模型」这一列是 v1.4 才第一次真正跑通的。此前所有标着 `huawei` 的跑分，
实际上都在跑规则引擎 —— 根因是 `.env` 从未被载入（见下方留痕表第 4 条）。

失败归因（跑分器自动分类）：`该澄清没澄清 ×5~6`、`常识错误 ×2`、`线索丢失 ×0~1`。

**必须如实说明的一处下降**：真实模型的「澄清判定正确率」25% 低于规则引擎的 50%。
R4 顺序修复后「1 个候选 + 置信 ≥0.6」改为直接输出，E06 一度从**误澄清**变成**漏澄清**。
但**该分母只有 4 条**，1/4 与 2/4 的差别不足以支撑任何结论。
扩充「应澄清」用例已列为下一步优先事项。

基线已写入 prompt 版本库（`prompt_versions` 表，版本号 `v1-rule`），
家属端「指标看板」页可直接看到这条记录 —— 后面每版 prompt 都往这张表追加一行。

> 命中率从 30% 爬到 60%+ 的**版本迭代曲线**是最重要的参赛资产：
> 每一版改了什么、验证什么假设、数字怎么变，全部留痕。
> — **数字的起点低不丢人，没有曲线才丢人。**

### 语音链路改造的 A/B 记录（v1 → v1.1）

接入华为云 SIS 语音识别后，发现一个**被语音引爆的既有缺陷**：
引擎的线索覆盖度用的是精确相等匹配，而语音返回的是自由文本 ——
患者说「我想喝水」，一个词都对不上词表里的「水」，整条链路会静默退回
`fallback_list`（没有候选、没有报错、没有任何提示）。

修复方式是在引擎入口加一层**线索归一化**（口语 → 词表原词），
三条通道（图标 / 关键词 / 语音）共用同一条规范化路径。

用环境变量开关做了可复现的 A/B：

| 指标 | 关闭归一化（基线） | 开启归一化 + 场景消歧 |
|---|---|---|
| Top-3 命中率 | 42.9% | **35.7%** ↓ |
| 平均澄清轮次 | 0.60 | 0.65 |
| 澄清判定正确率 | 50.0% | 50.0% |
| 紧急通道正确率 | 100% | **100%** |
| 整体通过率 | 50.0% | 45.0% |

**这个下降是真的，且已逐条归因 —— 不是回归，是评测标注与产品行为的张力：**

- 现有评测集 20 条的线索**全是词表原词**（按图标点选场景设计），
  所以归一化对它们几乎无影响 —— 分数变化只来自 1 条用例（E13）。
- E13：图标「电视」+ 关键词「戏」，期望映射到「戏曲」。
  场景消歧**正确地把「戏」映射成了「戏曲」**，正确答案置信度也确实上升了。
  但同时「电视」图标命中了另一条候选，两者仅差 **0.0021**
  （0.7538 vs 0.7517），低于 R4 的 0.1 差值阈值 → 触发二选一澄清。
- 这个澄清**从产品角度是合理的**（患者点了电视又说戏，确实该问一句），
  但该用例标注为 `expectClarify: false`（其意图是测「常用词映射」）。
- 单独用「戏」+ 娱乐场景时，top1 就是「我想看戏曲频道」且 `state=ready` ——
  证明消歧本身完全正确。

> **结论：要修的是评测集的判定口径（需要为语音自由文本补充用例、
> 并区分「合理澄清」与「过度澄清」），而不是回滚消歧能力。**
> 这条已固化为测试用例（`verify-normalize.js` 的 [8f] 组），
> 避免以后有人看到分数下降就误删这一层。

同时，本次改造修掉了一个**产品上最不能接受的失败模式**：
口语化紧急呼救「**快救救我**」此前会被静默判成 `fallback_list`。
根因是扫描词表时一命中「快」（level 2 紧急词）就短路返回，
把同义变体「救救我」→「救命」整个跳过。
修复后「快救救我」「救救我」「来人啊」「我摔了一跤」全部正确触发紧急通道，
且保持**零模型调用**。

### 核心技术发现：相似度算法几乎没有区分能力（v1.2 → v1.3）

这是本次迭代**最重要的一条发现**，值得单独一节。

评测判中、候选去重、模板对齐三处都建立在 `similarity()` 之上。
我们用 42 对**手工标注**的句子对去测它，结果是：

```
语义相同：0.00 ~ 0.40
语义不同：0.00 ~ 0.25
        ↑ 两个区间完全重叠 —— 不存在任何可用的判别阈值
```

具体到个案：

| 句子对 | 语义 | 旧算法得分 |
|---|---|---|
| 我头疼 / 头很疼 | 相同 | **0.0000** ← 只是加了一个「很」字 |
| 我左腿麻 / 我的左腿发麻 | 相同 | 0.1429 |

根因是**字符二元组 Jaccard 对中文近义词无效** —— 它比的是字面重合，而中文靠的是词义。
更严重的是：**这把坏尺子有三个下游消费者**，一处不准三处全偏。
因此此前所有 Top-3 数字，都是**在坏尺子上量出来的**。

**也就是说，这次不是「调参」，而是「先修尺子、再用尺子重新量」。**
不修尺子就去调阈值，只是让错的东西错得更稳定。

修法是**概念优先、字面兜底**的四信号加权：

```
概念重合 conceptSig（经归一化，可跨同义替换）  0.50
内容骨架 2-gram（去停用词/第一人称/情态词）    0.30
内容字集（去重后）                            0.15
原始字面 2-gram                               0.05
× 极性惩罚：否定不符 ×0.30 ／ 程度词不符 ×0.40
```

重新标定后：

- **同义最低 0.5000 > 异义最高 0.3333，间隔 0.1667** —— 终于存在可分区间
- 评测判中阈值 `0.42 → 0.35`
- 候选去重阈值 `0.7 → 0.45`（规则引擎内联的 `0.72 → 0.45`）

已固化为**永久守卫** `eval/verify-similarity.js`（40 条断言，含 v1.4 新增的时序确定性组）。
其中第 [6] 组专门**要求旧算法在 12 条同义句上失败过半**（实测失败 9/12）——
这组断言的作用是**防止有人把改好的尺子又改回去**。

> **教训：当指标不动时，先怀疑尺子，再怀疑被测对象。**
> 如果早一点去测 `similarity()` 本身的可分性，前面几轮的调参工作本可以省下。

### 🔴 我自己引入的竞态：异步初始化 × 同步函数

上一轮为「避免诊断脚本忘记注入归一化」，把依赖装配改成**动态 import 惰性自初始化**。
但这个改动**引入了一个比原问题更严重的缺陷**：动态 `import` 是异步的，
而 `similarity()` 是**同步**的 —— 在 promise 落定之前，概念集合返回空集，
相似度静默退化成纯字面比较；落定之后又恢复。

同一进程内实测（`scripts/repro-normalize-race.js`）：

| 句子对 | 未落定 | 落定后 | 漂移 |
|---|---|---|---|
| 我头疼 / 头很疼 | 0.2000 | **1.0000** | +0.8000 |
| 我左腿麻 / 我的左腿发麻 | 0.3893 | 1.0000 | +0.6107 |
| 我想喝水 / 我要喝水 | 0.9200 | 1.0000 | +0.0800 |

**4/4 对句子在同一进程内前后得分不同。**

产品后果比数字严重得多：**患者按下按钮的时机，会影响候选排序、进而影响是否澄清** ——
同一个人说同一句话，早零点几秒按就得到不同结果。这不是模型不稳定，是我们自己的时序 bug。

根因是**当初担心的循环依赖根本不存在**（已核验依赖图无环）：

```
normalize.js → scenarios.js（叶子，无依赖）
scoring.js   → intents.js
normalize.js ✗ 不 import scoring
intents.js   ✗ 不 import normalize / scoring
```

也就是说，动态 `import` 是在**解决一个不存在的问题**，却制造了一个真实的竞态。
修法是改回**静态 `import`**：归一化从模块加载的第一行起就同步可用，
不存在任何「尚未就绪」的时间窗。

> **教训：如果你为绕开某个约束而引入复杂性，先花两分钟验证那个约束是否真的存在。**
> 我为了「避免循环依赖」引入了异步加载，而循环依赖从来不存在 ——
> 代价是一个非确定性的产品行为。

### 🔴 模型自报置信度是噪声，却单独决定 R4 门槛

同一份提示词、同一组线索、连续 6 次调用，模型对**语义完全相同**的句子自报的置信度：

| 调用 | top1 文本 | `model_confidence` |
|---|---|---|
| 1 | 我要上厕所 | **0.62** |
| 2 | 我想去厕所，要换一下 | 0.76 |
| 3 | 我要上厕所 | **0.88** |
| 4 | 我想去厕所，帮我换 | 0.78 |
| 5 | 我想上厕所 | 0.82 |
| 6 | 我想去厕所 | 0.74 |

**同一句话「我要上厕所」，一次报 0.62、一次报 0.88，相差 0.26。**
`model_confidence` 没有经过任何校准，却带着 0.40 的权重、单独决定 R4 的 0.6 门槛 ——
这是设计缺陷，不是模型的问题。

实测后果（E06，toilet：厕所 + 换，连续 8 次）：

```
综合置信区间 = [0.5823, 0.7183]   极差 0.136
state 分布   = ready×7, clarifying×1
```

**患者说同样的话，得到「直接出候选」还是「被反问一句」，取决于模型抽签。**

修复：新增 `calibrateModelConfidence()` —— 把模型置信度**向中性值 0.5 收缩**
（`TRUST = 0.5`），只压缩幅度、不改变方向。
**权重表 `WEIGHTS` 与 R4 的 0.6 / 0.1 阈值一律未动**（对外契约）。
效果：E06 置信极差 **0.136 → 0.060**。

### R4 需要「确定性依据」，而不是指望模型恰好给低分

即便收缩了噪声，E06 仍不稳定 —— 因为它的**确定分量只有 0.265**，
距 0.6 差 0.335，**差额全靠模型噪声补足**。只要模型分量波动，就必然跨门槛。
这是**结构问题**，不是阈值问题。

正确的问法是：**E06 到底为什么应该澄清？** 答案是纯结构的，与模型无关：

- 线索「厕所」指向「我要上厕所」（`I-TOILET-01`）
- 线索「换」指向「帮我换一下尿不湿」（`I-TOILET-02`）
- **两条线索各自被完全不同的候选解释** —— 谁也不能替对方作证

于是新增 `detectClueConflict()`：**纯从句索与候选的对应关系判断，不依赖任何模型输出**。
判据是「是否存在两条线索，其归属候选集合完全不相交」。
若存在 → 客观歧义 → 必须澄清，且理由可复核、可复现、可向家属解释。

它在 `decideClarification()` 中**优先于全部置信度判定**，
因为它的可信度高于任何模型自报分数。

> 这正是 R4 原本想要的东西：**澄清是机制的一部分，
> 而不是「模型恰好给低分」的副产物。**
> 一个患者能否被正确澄清，不应该取决于模型的随机数。

已固化为**永久守卫** `eval/verify-conflict.js`（14 条断言），
分四组：真冲突必检出 / **互证线索不得误判为冲突**（防误伤）/ 判据与模型无关 / 引擎级行为。

### ⚠️ 仍未解决：模型用「复合意图」掩盖歧义

E06 在真实模型下**仍然不稳定**，但原因与原先判断不同，已重新定位：

模型的 top1 候选**总是同时覆盖两条线索** —— 例如
「我想去厕所，需要换一下」，`matched_clues = ["厕所","换"]`。
冲突检测据此判定「一条候选统一解释了全部线索」→ 不冲突 → 不澄清。

这是一个**产品语义问题**，而不是算法 bug：模型在用「复合意图」把歧义**抹平**了。
但患者同时按下「厕所」和「换」，很可能就是两个不同的意思 ——
ta 想去厕所，**同时**想让人帮忙换一下，或者只是想表达其中一件事。

**是否应把「线索被同一候选一并吸收」也视为可疑，属于规格级讨论，未擅自决定。**
这是下一版要和 A 确认的问题，已记录在此不回避。

### 同类缺陷的第四处：同义词表的语义反转陷阱

修相似度的过程中，误判分析顺带暴露出一个**与分数无关、但更危险**的问题：

```js
高兴: ['开心', '舒服', '挺好的', '不错', '心情好'],   // ❌
```

「不**舒服**」包含「舒服」→ 命中同义变体 → 被归一化成 **「高兴」**。
**语义完全反了。** 与之前「快救救我」被误判为 `fallback_list` 属同一严重级别 ——
都是**系统把患者的意思理解成相反的意思**。

修复：把「舒服」移出「高兴」组、移入「难受」组。

```
normalizeClue('左腿麻，有点不舒服')
  修复前 → ["麻","腿","难受","高兴"]     ← 同时既难受又高兴
  修复后 → ["麻","腿","难受"]
```

### 已知边界（主动划清，不回避）

- **繁体字暂不匹配**：词表只有简体，`廁所` 匹配不上 `厕所`。
  华为云 SIS 对中文返回简体，主链路不受影响；但若从别处粘贴繁体会落空。
  已固化为测试用例，作为待办而非静默行为。
- **评分模型无法区分 1 条与 2 条线索命中**：线索覆盖度是归一化比例
  （命中数/总数），所以 1/1 与 2/2 都等于 1.0。患者给 3 个互证线索时，
  系统的确信度本应更高，当前模型做不到。**未擅自改评分公式**（规格级改动），
  已记录为评测阶段的迭代目标。
- **单字歧义词不做无场景映射**：「关」在起居场景映射到「关灯」，
  在娱乐场景不动（该场景词表无含「关」的词），绝不跨界乱配。
- **「应澄清」用例只有 4 条**：分母太小，澄清判定正确率的波动（50% ↔ 25%）
  不足以下结论。扩用例是下一步的优先事项之一。
- **相似度仍有 7/42 误判**：最佳阈值 0.35 下仍有 7 条判错。
  设计上预留了 L2（大模型语义判定）只处理灰区，
  实测灰区占 **34.6%**（在刻意挑难的样本上）；**但 L2 绝不能进患者实时路径** ——
  患者按下按钮到看见候选的延迟是产品红线，不能拿大模型去赌。

### 已识别的边界（主动划清，不回避）

规则引擎在评测集上仍有 6 条「过度澄清」。逐条归因后确认：**其中 6 条属规格要求的正确行为** ——
这些样例的前两名综合置信度差值确实 < 0.1（如 E14 差 0.004、E04 差 0.016），
产物本就应有区分度不足的问题，**按 R4② 就该发二选一澄清**。

真正的差距在于：规则引擎靠关键词模式匹配打分，分数分布比大模型更集中，
因而更容易落进澄清区间。**接上华为云大模型后，这部分正是 prompt v2~v6 要爬升的空间** ——
评测集与跑分器已就位，每一版改动都可当场量化验证。

另有 2 条属澄清**类型**判定不符（E12 / E20 期望二选一、实际给了是否）：
这两条的 top1 置信度本身就低于 0.6，按 R4 规则优先级 ① 先于 ② 触发，
即「先问是不是，再问哪一个」在逻辑上是正确的降级顺序。
规格是否需要为「两名接近且都偏低」的情形定义更细的优先级，留下一版讨论。

### R4 判定顺序的设计缺陷（产品语义问题，不是代码 bug）

原实现里有一行：

```js
if (ranked.length < 2) return YES_NO;   // ❌ 无条件短路，且在置信判定之前
```

它把**两件完全不同的事**混为一谈：

| 表面现象 | 真实含义 | 应该做的事 |
|---|---|---|
| 去重后只剩 1 个候选 | 线索太少，系统没把握 | 澄清 |
| 去重后只剩 1 个候选 | **模型非常确信，其他都不沾边** | **直接说** |

候选数量**根本区分不了这两种情况** —— 唯一能区分的是**置信度**。
后果很具体：E07「我头疼」的置信度是 **0.6997**，远高于 R4 的 0.6 门槛，
却仅仅因为只有一个候选就被强制澄清 —— 患者被问了一句「你是想说我头疼吗」，
而系统本来已经知道答案了。**这是让患者多受一次罪。**

修复是**调换判定顺序**：

```js
if (ranked.length < 2) {
  if (top1.confidence >= CLARIFY_RULES.lowConfidence) return READY;  // 先问置信度
  return needClarify(YES_NO, ...);                                    // 不信才澄清
}
```

**R4 的 0.6 / 0.1 两个阈值一分未动** —— 它们是 R4 的对外契约，
改阈值能让数字变好看，但也就不算 R4 了。本次只改判定顺序。
效果：真实模型下被这一行杀掉的 4 条用例（**E03 / E07 / E11 / E13**）全部转为通过。

| 7 | **R4 判定顺序短路** | E07「我头疼」置信 **0.6997**（远高于 0.6）却被强制澄清 | `if (ranked.length < 2) return YES_NO` 是**无条件短路**，且放在置信判定**之前** —— 把「去重后剩 1 个 = 线索不足」与「去重后剩 1 个 = 模型很确信」混为一谈 | 改为**先看 top1 置信度**：≥0.6 直接输出，否则澄清。**阈值 0.6 / 0.1 一分未动**（对外契约）；4 条真实模型失败（E03/E07/E11/E13）全部出自这一行 |
| 8 | **线索覆盖度精确匹配** | 候选「我急着要上厕所」不含词表原词「厕所」→ 覆盖度 0 → 模型给的 0.93 被稀释成 0.49 → 被迫澄清 | `clueCoverageScore()` 里 `pool.has(clue)` 直接相等比较，而比较对象是模型生成的自由文本 | 比较前先把候选文本归一化成概念；归一化不可用时才退回宽松子串匹配（避免重蹈「开灯」/「灯」的回归）。覆盖度 0→1，置信 0.49→0.76 |
| 9 | **模型候选丢失模板归属** | 模型生成的候选没有 `_templateId` → 场景先验（0.20）与个性化加权（0.15）合计 **0.35 的权重被静默丢弃** | `compositeConfidence` 找不到模板，静默用默认先验 | 新增 `alignTemplate()`：同场景优先、全局兜底，用新相似度在模板文本/示例/id 三处取最大；阈值 0.2，兜底 `prior: 0.5`。先验 0.5 → 0.7576 |
| 10 | **归一化竞态（我上一轮自己引入的）** | 同一进程内，「我头疼」vs「头很疼」前一次 0.2000、后一次 1.0000；**4/4 对句子漂移** | 把归一化改成**动态 import 惰性初始化**（异步），而 `similarity()` 是**同步**函数 —— promise 落定前概念集为空，静默退化为字面比较。**当初担心的循环依赖根本不存在**（依赖图无环，已核验） | 改回**静态 import**，归一化从模块加载第一行起同步可用，消除「未就绪」时间窗；`verify-similarity.js` 新增 [0] 组时序确定性守卫，锁死「模块加载瞬间 === 事件循环稳定后」 |
| 11 | **模型自报置信度是噪声** | 同一份提示词连续 6 次，模型对同一句「我要上厕所」自报 **0.62 / 0.88**（相差 0.26）；E06 综合置信在 [0.5823, 0.7183] 漂移，8 次里 7 ready / 1 clarifying | `model_confidence` 未经任何校准，却带 0.40 权重、**单独决定 R4 的 0.6 门槛** —— 患者得到什么行为取决于模型抽签 | 新增 `calibrateModelConfidence()`：向中性值 0.5 收缩（`TRUST=0.5`），只压幅度不改方向。**权重表与 0.6/0.1 阈值一律未动**。E06 极差 0.136 → 0.060 |
| 12 | **R4 缺少确定性澄清依据** | E06（厕所 + 换）的确定分量仅 0.265，距 0.6 差 0.335，差额**全靠模型噪声补足** → 「是否澄清」由噪声决定 | 澄清裁决完全建立在置信度上，而置信度里混着模型噪声；线索本身是否存在客观歧义，从未被单独判断 | 新增 `detectClueConflict()`：纯结构判断，「是否存在两条线索其归属候选集合完全不相交」。真歧义 → 直接澄清，**优先于全部置信度判定**；理由可复核、可解释。永久守卫 `eval/verify-conflict.js`（14 条），含**互证线索不得误判**的防误伤组 |
| 13 | **确定性结论出不了后端** | `detectClueConflict` 的结论只活在 `engine.js` 的 `trace` 里，`routes.js` 在 API 边界把它整个丢掉 —— 刚做出来的确定性依据，页面上一个字也看不到 | `routes.js` 的患者端响应是手工挑选字段的（有意为之，防止 R3 被绕过），新增的 `trace` 字段没人透出去 | 在**不放任何数字**的前提下透出 `clueConflict`（结构化 `pairs`，非句子，避免措辞改动拗断前端）；澄清卡用 `describeClueConflict()` 讲成人话；家属端落库并单列展示。新增永久守卫 `eval/verify-patient-wording.js`（31 条） |
| 14 | **补列迁移缺失** | 新代码 `SELECT clue_conflict` 会直接抛错 | `CREATE TABLE IF NOT EXISTS` **不会给已存在的表补列** —— 本地跑过的 SQLite、线上已启动的容器都是老结构 | 新增幂等 `addColumnIfMissing()`（`PRAGMA table_info` 查列 + `ALTER TABLE`）；用**手写的老库结构**验证过自动补列与二次打开幂等，不是只测新库 |

> **第 13 条是一个反复出现的模式**：后端算出了结论，但没人在边界上把它送出去。
> 这类缺陷的特点是**所有单测都绿**（引擎确实算对了），而**产品上完全不可见**。
> 教训：**给引擎加输出的同时，必须问一句「它到得了界面吗」。**
> 本次把 `pairs`（结构化）而不是 `detail`（自然语言句子）透给前端，
> 就是为了让「后端改措辞」不再可能拗断「前端渲染」。

> **第 10 条必须单独警示：这是我上一轮为了修一个小问题而引入的、更严重的缺陷。**
> 产品后果是「患者按键的时机决定 ta 得到候选还是被反问」，而这与 ta 说了什么**完全无关**。
> 教训：**为绕开某个约束而引入复杂性之前，先花两分钟验证那个约束是否真的存在。**
> 我为「避免循环依赖」引入了异步加载，而循环依赖从来不存在。
>
> **第 11 与第 12 条是同一个问题的两面**，也是本次最有价值的方法论收获：
> 第 11 条说明「**不要把未经校准的模型自报数字直接当作产品决策的闸门**」；
> 第 12 条给出正确做法 —— 「**把澄清建立在可复核的结构事实上，而不是模型的随机数上**」。
> 这两条合起来改变了 R4 的性质：澄清从「分数恰好低于阈值」的副产物，
> 变回「线索客观存在歧义」的必然结果。**这才是 R4 原本想要的东西。**
>
> **第 5 条是本次最重要的技术发现**：它证明**此前的所有 Top-3 数字都是在坏尺子上量出来的**。
> 这把坏尺子有三个下游消费者 —— ① 评测判中口径 ② 候选去重 ③ 模板对齐 ——
> 一处不准，三处全偏。因此本次改动不是「调参」，而是**先修尺子、再用尺子重新量**。
> 已固化为永久守卫 `eval/verify-similarity.js`（40 条断言），其中专门有一组
> 断言**要求旧算法在同义句上失败过半** —— 防止有人把好尺子改回坏尺子。
>
> **第 7 条是产品语义层面的设计缺陷，不是代码 bug**：
> 把「候选只有 1 个」等同于「信息不足」是一种直觉上的偷懒。
> 候选少既可能是**线索太少**（该澄清），也可能是**模型非常确信、其他都不沾边**（该直接说）。
> 二者不可由候选数量区分，**必须问置信度**。这条修复让规则引擎 Top-3
> 从 35.7% → **64.3%**，全凭调整判定顺序、未动任何阈值。
>
> **第 6 条与第 8 条属于同一缺陷类：字面匹配在自由文本上必然出错。**
> 本次共找到**四处**同类实例（入口归一化、覆盖度比较、相似度本身、同义词表）。
> 共同的教训是：**只要比较的两端有一端来自模型生成，任何形式的精确相等/子串包含都不成立。**
>
> **第 1 条是本次最严重的缺陷**，且**跑分器完全测不出来** ——
> 评测集判的是「候选有没有命中标准答案」，不判「患者点/答之后系统怎么响应」。
> 数字全绿，但患者说「不是」反被系统确认成「是」，这等于**系统代替患者撒谎**，
> 直接违反产品立意。已补 `test-contracts.js` 专门守住这类**机制契约**，
> 与评测集（测准确率）分工明确：一个守底线，一个爬上限。
>
> 第 2 条同样值得记：当时把它判成「只是 shell 显示问题」是错的 ——
> 请求侧乱码和已落库脏数据是两件事。演示前必须重置现场。

### 测试与评测的分工

```bash
npm run test:all   # 全部守卫（40 + 75 + 40 + 14 + 31 + 32 + 客户端 + 端到端 = 269 条）
npm test           # 机制契约回归（40 条）—— 守红线，挂一条就是产品做了不该做的事
npm run eval       # 评测集跑分（20 条）—— 爬指标，产出 Top-3 命中率与澄清轮次
```

细分守卫：

| 命令 | 守什么 |
|---|---|
| `npm test` | 机制契约 40 条 —— **R1~R8 红线**（守底线） |
| `npm run test:normalize` | 归一化层 75 条 —— 口语/同义/场景消歧 |
| `npm run test:similarity` | 相似度判别力 40 条 —— 含**时序确定性**与「旧算法必须失败」回归护栏 |
| `npm run test:conflict` | 线索冲突 14 条 —— R4 的**确定性澄清依据**，含互证防误伤 |
| `npm run test:wording` | 患者端措辞契约 31 条 —— **R3 不得被绕过**、解释只引用患者自己的词、**只扫字符串字面量**（注释里解释「为什么禁用某词」不算违规） |
| `npm run test:speech-visual` | 语音视觉通道 32 条 |
| `npm run test:speech` / `test:client` / `test:e2e` | SIS 链路、前端采集、端到端 |

诊断脚本（排查非确定性问题时用）：

```bash
npm run diag:race         # 归一化竞态复现（模块加载瞬间 vs 事件循环稳定后）
npm run diag:determinism  # 模型输出稳定性（同一输入重复 N 次）
npm run diag:variance     # 候选数/置信度/state 分布统计
npm run diag:r4           # R4 四条分支的逐项体检
```

评测集关注**答得准不准**，契约测试关注**有没有越界**。
而诊断脚本关注第三件事：**结论是否可复现** ——
本次三个最严重的缺陷（竞态、模型噪声、澄清无确定依据）都是靠它们发现的，
且**跑分器与契约测试都测不出来**（数字全绿但行为不可复现）。

## 部署

容器化部署（对应华为云容器化部署，答辩环境替换镜像即可）：

```bash
docker build -t shiyan-revoice:0.1.0 .
docker run -p 8080:8080 -e MODEL_PROVIDER=huawei \
  -e HW_MAAS_API_KEY=$HW_MAAS_API_KEY \
  -e HW_MODEL_ENDPOINT=$HW_MODEL_ENDPOINT -e HW_MODEL=$HW_MODEL \
  shiyan-revoice:0.1.0
```

镜像内置 `HEALTHCHECK` 打 `/api/health`，健康检查同时回报当前 provider 与 prompt 版本号。

生产环境替换清单（数据层已按同一套键语义实现，上层代码不动）：

| 本地实现 | 华为云 | 替换位置 |
|---|---|---|
| `node:sqlite`（`data/revoice.db`） | RDS（MySQL / PostgreSQL） | `server/data/db.js` |
| 进程内 LRU 缓存 + 命中统计 | Redis（`patientId\|scenario\|icons\|keywords\|fragments` 键） | `ClueCandidateCache` |
| 规则引擎 | 华为云大模型 API | `server/model/providers/huawei.js` |
